# 設計

[docs/spec.md](spec.md) を実現するための設計。細部は実装しながら更新する。
「実機で確かめること」に挙げた項目は推測で書いており、実機で確かめた結果で確定する。

この設計は、別のコンテキストによる後追いレビュー（[#27](https://github.com/usa0w0/cornix-keymapper/issues/27)）を受けて直している。

## 方針

- 利用者が編集するのは「キーごとの動作」（タップ・長押し・2回タップ・タップ後長押し）だけにする。Vial のキーコードや Tap Dance の番号は、読み込み時と書き込み時にだけ変換して作る
- 利用者が変えていない設定は、本体から読んだ値のまま書く。変換し直した値を使わない。「編集しなければ変わらない」を、テストだけでなく状態の持ち方で保証する
- 通信（Vial）、変換と枠管理（純粋なロジック）、書き込みの手順、画面（React）を分ける。画面以外は実機なしで自動テストできる形にする
- 実機がなくても画面を開発・確認できるよう、本体の代わりになる偽の機器（メモリ上の実装）を用意する
- 依存ライブラリは最小限にする。状態管理や UI のライブラリは入れない

## 技術構成

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| 言語・UI・ビルド | TypeScript 7、React 19、Vite 8 | 仕様の指定 |
| パッケージ管理 | npm、Node.js 24（`.nvmrc`） | 追加の道具が要らない |
| テスト | Vitest | Vite の設定をそのまま使える |
| lint | oxlint | Vite の雛形の既定 |
| スタイル | 素の CSS（全体に効く1つのファイル `src/index.css`） | 画面数が少なく、UI ライブラリの学習が不要。部品ごとに分ける方式（CSS Modules）にするかは、画面デザインが決まった時に見直す |
| 状態管理 | React の `useReducer` と Context | 状態は少数で、置き場は「状態の置き場」の表のとおり |
| CI | GitHub Actions（lint、型検査、テスト、ビルド） | PR ごとに実行 |
| 公開 | GitHub Pages（`main` と `develop` への push で Actions からデプロイ） | 仕様の指定。public リポジトリの無料枠内 |

公開先は次の2つ。GitHub Pages は1リポジトリに1サイトなので、デプロイのたびに両方をビルドして1つのサイトにまとめる。

| 版 | 元のブランチ | URL |
| --- | --- | --- |
| リリース版 | `main` | `https://usa0w0.github.io/cornix-keymapper/` |
| 開発版 | `develop` | `https://usa0w0.github.io/cornix-keymapper/dev/` |

Vite の `base` は `/cornix-keymapper/` で、開発版だけビルド時に `--base=/cornix-keymapper/dev/` を渡す。開発版は見出しに「開発版」と表示する。

2つの版は同じオリジンなので、`localStorage` を共有する。ブラウザ内に保存するデータのキーには `import.meta.env.BASE_URL` を含め、版ごとに分ける。

## 層と依存の向き

矢印は「左が右を使う」を表す。

```
ui ──▶ session ──▶ model ──▶ device/types（インターフェースと型だけ）
 │        │                        ▲
 │        └──▶ storage ──▶ model   │ 実装
 └──▶ model、storage、device/types │
                              device/vial ──▶ WebHID
                              device/fake（開発・テスト用）

main.tsx ──▶ device/vial か device/fake を選んで ui に渡す
```

```
src/
  main.tsx           起動。使う機器の実装（Vial / 偽の機器）をここで選ぶ
  browserSupport.ts  対応ブラウザーの判定
  device/            機器との通信
    types.ts         インターフェースと型（DeviceConnector、KeyboardDevice、KeyboardSnapshot、失敗の種類）
    vial/            Vial の実装。通信だけを受け持つ
      transport.ts   WebHID の送受信（32 バイトの要求と応答、直列化、タイムアウト、応答の突き合わせ）
      connect.ts     機器の選択と接続（DeviceConnector の実装）
      commands.ts    VIA / Vial のコマンド
      definition.ts  レイアウト定義（XZ 圧縮の JSON）の展開と解釈
      vialDevice.ts  KeyboardDevice の実装
    fake/            メモリ上の偽の機器。失敗をわざと起こせる
  model/             純粋なロジック（React にも WebHID にも依存しない）
    keycodes.ts      Vial のキーコード（数値・名前）と動作（Action）の相互変換
    action.ts        動作の型と分類・日本語の表示名・検索
    behavior.ts      キーの動作（4欄）の型
    decode.ts        本体の設定 → キーの動作
    encode.ts        キーの動作 → 本体の設定（機能の自動判定、枠の割り当て）
    diff.ts          利用者に見せる変更点の一覧、機器に送る操作の計算
    transparent.ts   透過キーで実際に効く動作の解決
  session/           手順（React にも WebHID にも依存しない）
    editState.ts     編集中の状態
    writeSession.ts  書き込みの手順（読み直し、バックアップ、書き込み、照合、再試行、復元）
  storage/
    vil.ts           .vil の読み書き
    backup.ts        ブラウザ内の自動バックアップ
  ui/                React のコンポーネント
```

決まり:

- `ui`、`session`、`model`、`storage` は `device/types.ts` だけを見て、`device/vial` と WebHID を直接は参照しない。`device/vial` を読み込むのは `main.tsx` だけにする
- `session` は、機器（`KeyboardDevice`）とバックアップの保存先を外から受け取る。偽の機器と偽の保存先を渡して、手順を自動テストできるようにする
- `device/vial` は通信だけを受け持ち、キーコードの意味は扱わない

別のプロトコルの機器への対応は、この設計では考えない（仕様の「将来の検討事項」）。対応すると決めた時に設計し直す。層を分けるのは、偽の機器で画面を開発するためと、画面以外を自動テストするためである。

## 機器のインターフェース

本体の状態を、まとめて1つのスナップショットとして読む。書く時は、差分だけを操作の列として渡す。

```ts
interface KeyboardSnapshot {
  uid: string                      // 機器の識別（バックアップの鍵、.vil の照合）
  layout: LayoutDefinition         // キーの位置と大きさ、エンコーダーの位置
  capabilities: Capabilities       // レイヤー数、Tap Dance / Combo の枠数、Vial の版
  keymap: number[][]               // [レイヤー][キー] = キーコード
  encoders: [number, number][][]   // [レイヤー][エンコーダー] = [左回し, 右回し]
  tapDances: TapDanceEntry[]       // 枠数ぶん。4つのキーコードと時間の値
  combos: ComboEntry[]             // 枠数ぶん
}

interface DeviceConnector {
  connect(): Promise<KeyboardDevice | null>   // 機器選択を開いて接続する。選ばずに閉じたら null
}

interface KeyboardDevice {
  name: string                                           // 画面に出す機器名
  protocol: string                                       // 画面に出す通信方式（例: VIA プロトコル 9）
  onDisconnect(listener: () => void): () => void         // 切断の通知
  read(onProgress): Promise<KeyboardSnapshot>
  write(operations: WriteOperation[], onProgress): Promise<void>   // 渡された順に書く
  disconnect(): Promise<void>
}

// 1キー、1エンコーダー、1枠、1コンボを書く操作
type WriteOperation = /* setKey | setEncoder | setTapDance | setCombo */

// 失敗の種類。画面はこれを見て文言を出す
type DeviceErrorKind = 'timeout' | 'send-failed' | 'disconnected' | 'unexpected-response'
```

- スナップショットは「本体の表現」のまま持つ（キーコードは数値、Tap Dance は番号付き）。`.vil` とバックアップも同じスナップショットから作るので、このサイトが解釈できないキーコードも失わない
- 読み出しをまとめて1つにするのは、バックアップ、照合、差分の単位をそろえるため。書き込みを差分だけにするのは、Bluetooth での通信の回数と、本体が書きかけの状態でいる時間を短くするため
- `write` は途中で失敗したら、何番目の操作で、どの種類の失敗かを返す
- このサイトで扱わない設定（マクロ、Key Override、QMK Settings）は読まないので、スナップショットに入らない。キーに割り当てられた対象外のキーコード（マクロを呼ぶキーなど）は、`keymap` の数値として残る

## Vial の通信

- WebHID で、usage page `0xFF60`・usage `0x61` の HID インターフェースを `navigator.hid.requestDevice` のフィルターに指定する。USB と Bluetooth で同じ指定を使う
- 32 バイトの要求を送り、32 バイトの応答を1つ受け取る。要求は1つずつ直列に処理し、応答が来なければタイムアウトで失敗にして1回だけ再送する
  - 応答を待つ時間は 1 秒。実機で Bluetooth の応答時間を測ったら、その値から決め直す
  - 出力レポートの ID は、機器が申告するレポートの情報から取る（なければ 0）
- 応答の取り違えを防ぐ。応答には、どの要求への応答かを示す印がなく、遅れて届いた応答を次の要求の応答と取り違えると、以後の読み出しが1つずつずれ続ける。待つだけでは防げないので、次の3つを行う
  - 応答の中身で要求と突き合わせる。応答の先頭が要求と同じ内容を返すコマンドは、一致を確かめ、合わない応答は捨てる（どのコマンドが返すかは実機で確かめる）
  - タイムアウトが1回でも起きたら、次の要求の前に同期をやり直す。VIA `0x01` を送り、先頭が `0x01` の応答が返るまで、届いた応答を捨てる
  - 読み出しの途中でタイムアウトが起きたら、その読み出しで得た内容を捨てて、最初からやり直す
- 接続時に VIA `0x01`（プロトコルの版）を1回送り、先頭が `0x01` の応答が返ることを確かめてから「接続済み」にする
- 切断は `navigator.hid` の `disconnect` イベントで検知し、`KeyboardDevice.onDisconnect` で知らせる
- 同じ機器を、複数のタブや Vial と同時に開いた時に応答がどう届くかは、実機で確かめて扱いを決める。決まるまでは、同時に開かないよう画面で案内する
- 使うコマンド

| 目的 | コマンド |
| --- | --- |
| 接続の確認、UID と Vial の版 | VIA `0x01`、Vial `0xFE 0x00` |
| レイアウト定義 | Vial `0xFE 0x01`（大きさ）、`0xFE 0x02`（32 バイトずつ） |
| レイヤー数、キーマップ | VIA `0x11`、`0x12`（まとめ読み）、`0x05`（1キー書き込み） |
| エンコーダー | Vial `0xFE 0x03`（読み）、`0xFE 0x04`（書き） |
| Tap Dance と Combo の枠数 | Vial `0xFE 0x0D 0x00` |
| Tap Dance | Vial `0xFE 0x0D 0x01`（読み）、`0x02`（書き） |
| Combo | Vial `0xFE 0x0D 0x03`（読み）、`0x04`（書き） |

- レイアウト定義は XZ 圧縮されている。ブラウザーに XZ の展開機能はないため、展開だけを行う小さなライブラリを1つ入れる（候補: `xz-decompress`。実機の定義を展開できるか確かめて決める）
- 定義の `layouts.keymap`（KLE 形式）から、キーの座標・行列上の位置・エンコーダーを取り出して描画する。配列はコードに持たない
- マクロ、Key Override、QMK Settings のコマンドは使わない

### 対応機能の判定

| 機能 | 判定の方法 |
| --- | --- |
| Tap Dance、Combo | 本体から読んだ枠数。0 なら使えない |
| ロータリーエンコーダー | 本体から読んだレイアウト定義に含まれるか |
| レイヤー切替の方式（MO・TG・TO・OSL） | 本体から取得するコマンドがないため、実機で確かめた結果を、Vial の版ごとの表としてサイトに持つ。表にない版では、4つとも選べるようにしたうえで、確かめていない版だと画面に出す |

## キーの動作のモデル

```ts
type Action =
  | { kind: 'key'; code?: number; mods: Mod[] }           // 文字・修飾キー・ショートカット・メディアなど
  | { kind: 'layer'; mode: 'momentary' | 'toggle' | 'to' | 'oneShot'; layer: number }
  | { kind: 'transparent' }
  | { kind: 'none' }
  | { kind: 'unsupported'; raw: number; label: string }   // マクロなど。編集不可、上書きは可

interface KeyBehavior {
  tap?: Action
  hold?: Action
  doubleTap?: Action
  tapHold?: Action
}
```

- `code` は、Vial のキーコードのうち、修飾を含まない基本キーの番号。番号の体系が QMK 版 Vial と同じかは実機で確かめる
- `Mod` は、修飾キーの種類（Ctrl・Shift・Alt・GUI）と左右の組
- 「ショートカット」は修飾キー付きのキー（例: Ctrl+C）として、`code` と `mods` の両方を入れる
- 修飾キーだけの動作（Ctrl だけ、Ctrl+Shift だけ）は、`code` なしで `mods` だけを入れる
- 4欄はどれも「なくてもよい」。ただし、少なくとも1つは入れる。何も割り当てないキーは、タップ欄に「透過」か「何もしない」を入れる
- 「透過」と「何もしない」は、タップ欄にだけ入れられ、ほかの欄と組み合わせられない。「長押しだけ」のキーは、タップ欄を空にして表す
- 「押している間だけレイヤー N」（`momentary`）は、長押し欄とタップ後長押し欄にだけ入れられる。タップ欄に入れても同じキーコード（MO）になり、読み直すと長押し欄に移って見えるため
- エンコーダーの左回し・右回しと、コンボの出力は、`Action` 1つで表す。Tap Dance を指すキーコードなど、`Action` で表せないものは `unsupported` になる

## 状態の置き場

| 状態 | 置き場 | いつ作るか | いつ捨てるか |
| --- | --- | --- | --- |
| 接続（接続中の機器、接続の状態、切断の知らせ） | 画面の最上位（`App` が `useConnection` で持つ） | 接続した時 | 切断した時 |
| 基準（本体から読んだスナップショット） | 編集中の状態（`session/editState.ts`、`useReducer`） | 読み出しが終わった時 | 読み直した時、別の機器（UID が違う）をつないだ時 |
| 出発点（編集の土台にするスナップショット） | 同上 | 基準と同じものを入れる。`.vil` やバックアップを読み込んだ時は、その内容に入れ替える | 基準と同じ |
| 編集（利用者が変えたキー、エンコーダー、コンボ） | 同上 | 利用者が編集した時 | 書き込みと照合が通った時、取り消した時 |
| 読み出しの進み具合 | 画面の最上位 | 読み出しの間 | 読み出しが終わった時 |
| 書き込みの進み具合、失敗後の状態（目標、失敗した項目） | 書き込みの手順（`session/writeSession.ts`） | 「書き込み」を押した時 | 照合が通った時、「戻す」が終わった時 |
| バックアップ、「書き込み中」の印 | `localStorage`（`storage/backup.ts`） | 書き込みの最初 | 「保存」の節のとおり |

編集中の状態は、基準・出発点・編集の3つからなる。

```ts
interface EditState {
  baseline: KeyboardSnapshot   // 基準: 本体から読んだもの。変更点の一覧を作る相手
  source: KeyboardSnapshot     // 出発点: 通常は基準と同じ。.vil やバックアップを読み込むと入れ替わる
  edits: Edits                 // 利用者が変えたものだけ（キーは KeyBehavior、エンコーダーとコンボの出力は Action）
}
```

- 書き込む目標は「出発点に、編集を当てはめたスナップショット」である。編集していないキー、エンコーダー、コンボ、Tap Dance の枠は、出発点の値をそのまま使う。画面に出す時だけ、キーの動作に変換する
- Tap Dance の番号は、編集には持たない。目標を作る時に「枠の割り当て」で決める
- 接続が切れても、基準・出発点・編集は捨てない。つなぎ直したら読み直し、基準と同じなら編集を続ける。違えば「本体の設定が変わっています」と示し、読み直した内容に編集を当て直すか、編集を捨てるかを選ばせる。別の機器（UID が違う）なら、編集を捨てる前に確認する
- 書き込みの失敗後の状態も、つなぎ直しをまたいで残す
- ページの再読み込みや閉じる操作では、編集は消える。編集がある間は、ブラウザーの「このページを離れますか」の確認を出す。編集中の内容はブラウザーに保存しない（仕様の「保存先」が、本体、`.vil`、自動バックアップに限られるため）

## 機能の自動判定

### 書き込む時（`KeyBehavior` → キーコード）

編集したキーにだけ行う。上から順に当てはめ、最初に合ったものを使う。

| 条件 | 使う機能 | 枠 |
| --- | --- | --- |
| タップだけ | そのキーコード1つ（タップ欄がレイヤー切替なら TG・TO・OSL のキーコード） | 不要 |
| 長押しだけで、長押しが「押している間だけレイヤー N」 | MO(N) | 不要 |
| タップ＋長押しで、タップが修飾なしの基本キー、長押しが片側の修飾キーの組み合わせ | MT | 不要 |
| タップ＋長押しで、タップが修飾なしの基本キー、長押しが「押している間だけレイヤー N」（N は 0〜15） | LT | 不要 |
| 上記以外 | Tap Dance | 1つ |

MT と LT はキーコードの形に制約がある（タップ側は修飾なしの基本キーだけ、MT の修飾は左右どちらか片側だけ）。制約に合わない組み合わせは Tap Dance に回す。

### 読み込む時（キーコード → `KeyBehavior`）

逆向きに変換する。MO は長押し欄、MT と LT はタップ欄と長押し欄、Tap Dance は4欄に展開する。TG・TO・OSL はタップ欄のレイヤー切替になる。対象外の機能（マクロ、DF、TT など）と解釈できないキーコードは `unsupported` として元の値を保持する。

読み込む時の変換は、画面に出すためだけに使う。編集していないキーは、出発点のキーコードをそのまま書くので、MT で書ける内容が Tap Dance で設定されていた場合なども、元の表現のまま残る。

読み込んだ直後に何も編集せずに作った目標が、基準のスナップショット全体（キーマップ、エンコーダー、Tap Dance の枠、コンボ）と一致することを、テストで確かめる。

### 枠の割り当て

枠の番号は編集に持たず、目標を作るたびに決める。

- 枠が「使われている」とは、キー、エンコーダー、コンボの出力のどれかから指されていることをいう。`unsupported` として残っているキーコードが指す枠も含める
- 出発点で中身が入っている枠は、どこからも指されていなくても、勝手に空にしない（Vial で作りかけの枠を消さないため）
- 出発点にある枠どうしは、内容が同じでもまとめない。時間の値も枠ごとに残す
- 編集したキーが Tap Dance を必要とする時は、次の順で枠を決める
  1. 4欄が同じ内容の枠が出発点にあれば、その枠を使う（＝同じ内容のキーは1つの枠を共有する。複数あれば番号の小さいもの）
  2. なければ、空いている枠（出発点で中身が空で、どこからも指されていない枠）を使う
  3. なければ、この編集で使われなくなった枠を使う
- この編集で使われなくなった枠（出発点では指されていて、目標ではどこからも指されない枠）は、空にする
- 新しく使う枠の時間の値は、既存の枠と同じ値を入れる想定（実機で確かめる）

必要な枠の数が足りない編集は、状態に反映する前に計算して止め、枠を使っているキーの一覧を出す。出発点で中身が入っているのにどこからも指されていない枠があれば、その枠を上書きして使うかを選ばせる。残り枠数（空いている枠の数）は同じ計算から表示する。

共有は「同じ枠を指している」ことで決まる。共有中のキーを編集する時は、同じ枠を指すほかのキーの位置を示して確認する。「連動して変更」は、同じ枠を指すキーすべてに同じ編集を適用すること、「このキーだけ変更」は、選んだキーだけを編集すること（内容が分かれるので枠が1つ増える）として実装する。枠を使わない機能（MT、LT など）で同じ内容になっているキーは、共有ではないので確認を出さない。

## コンボ

Vial のコンボは、キーの位置ではなくキーコードの組（最大4つ）と出力のキーコードで定義される。

- 方針: 画面では「クリックしたキーの位置」で入力し、編集中の状態でも位置の組で持つ。キーコードに直すのは目標を作る時だけにする。こうすると、コンボに使っているキーのタップを後から変えても、コンボが付いてくる（Tap Dance の番号を隠すのと同じ考え方）
- 位置で持つには、位置をどのキーコードに直すかが決まっている必要がある。次の2点を実機で確かめてから、持ち方を確定する
  - どのレイヤーのキーコードで判定されるか
  - 長押しなどを設定したキー（MT、LT、Tap Dance）をコンボに使うと、何のキーコードで判定されるか
- 読み込み時は、キーコードが一致する位置を探して図に示す。一致する位置が複数ある時は、候補をすべて示す。一致する位置がないコンボは「対応するキーがない」と表示する
- 編集していないコンボは、出発点の値をそのまま書く
- 枠が足りない時の扱いと残り枠数の表示は、Tap Dance と同じにする（足りない編集は止め、使っているコンボの一覧を出す）

## 書き込みの流れ

手順は `session/writeSession.ts` が受け持つ。画面は、進み具合と結果を表示し、利用者の選択を渡すだけにする。書き込みの間は、編集とほかの操作を止める。

差分は2種類あり、別のものとして扱う。

| 名前 | 中身 | 作り方 | 使い道 |
| --- | --- | --- | --- |
| 変更点の一覧 | キーの動作の言葉での前後（例: 「レイヤー1 の左手 3 行目 2 列目: 長押しを Ctrl から Shift に変更」） | 基準と目標を、それぞれキーの動作に変換して比べる | 利用者の確認 |
| 機器に送る操作（`WriteOperation[]`） | 本体の表現での書き込み（1キー、1枠など） | 目標と、本体の現在値を比べる | `KeyboardDevice.write` |

1. 変更点の一覧を表示する。キーの動作の言葉で表せない変更（枠を空にする、など）も一覧に出す
2. 取り消しの単位は、利用者の編集1回とする。「連動して変更」は1件として取り消す。`.vil` やバックアップから読み込んだ内容は、全体を1件として取り消す（出発点を基準に戻す）
3. 「書き込み」で、まず本体から現在の設定を読み直す。基準と違っていたら、もう一度読んで確かめる。それでも違えば書き込みを止め、「本体の設定が、読み込んだ後に変わっています」と示して、読み込み直すか、そのまま上書きするかを選ばせる
4. 読み直した内容をバックアップし、「書き込み中」の印を保存する。保存した直後に読み戻して確かめ、保存できなければ書き込みを始めない
5. 機器に送る操作を作り、次の順に書く
   1. 本体でいまどこからも指されていない Tap Dance の枠への書き込み（新しく使う枠）
   2. キーマップ、エンコーダー、コンボ
   3. 残りの Tap Dance の枠（使われなくなった枠を空にする、など）
6. 全体を読み直し、目標と照合する。一致したら「書き込み中」の印を消し、読み直した内容を新しい基準にする
7. 途中の失敗と照合の不一致は、失敗した項目と原因（切断、タイムアウト、不一致の箇所）を示し、「再試行」と「書き込み前の状態に戻す」を出す
   - 再試行: 本体を読み直し、目標との差分を作り直して書く。バックアップは取り直さない
   - 戻す: 本体を読み直し、4 で取ったバックアップとの差分を書く。キーの動作への変換は通さない

5 の順序にする理由は、途中で失敗した時に、触っていないキーの動作を変えないためである。キーが指している枠を先に空にすると、キーマップを書く前に失敗した時に、そのキーが効かなくなる。空いている枠がなく、使用中の枠の中身を書き換えるしかない場合は、途中の状態が避けられないので、書き込み前の確認でそう伝える。

どの操作も「目標のスナップショットと本体の現在値との差分を、5 の順に書く」という同じ処理で実現する。

書き込みの途中でページを閉じた、ブラウザーが落ちた、などで「書き込み中」の印が残った場合は、次に同じ機器を接続した時に「前回の書き込みが終わっていません」と示し、バックアップの状態に戻すか、いまの本体の状態のまま続けるかを選ばせる。

## 読み出しの流れ

- 接続したら、スナップショットを読み出して基準にする。進み具合を表示する
- 途中で失敗したら、読んだ内容は捨てる。失敗の種類（切断、タイムアウト）と、「もう一度読み出す」を表示する。読みかけの内容は画面に出さない

## 保存

### `.vil`

- Vial の JSON 形式。スナップショットと相互変換する。Vial の `.vil` はキーコードを名前の文字列で持つ想定なので、名前と数値の対応表を `model/keycodes.ts` に持つ（実物のファイルで確かめる）
- 読み込んだ `.vil` は、いきなり書き込まず、編集中の状態の「出発点」に入れ、通常の書き込みの流れ（変更点の確認）を通す
- 読み込みを止めて理由を示す場合: UID が接続中の本体と違う、レイヤー数・キー数・エンコーダーの数が合わない、Tap Dance か Combo の枠数が合わない
- マクロ、Key Override、QMK Settings は `.vil` に含めない
  - 保存する時は「マクロなどは、このファイルに含まれません」と表示する
  - 読み込んだファイルに含まれていた時は、「このファイルのマクロなど N 件は、本体に書き込まれません」と表示する。中身は保持しない
  - 理由: 仕様の「やらないこと」であり、本体から読むコマンドを使わないため。このサイトで保存した `.vil` を Vial で書き戻すと、マクロなどが空になるおそれがあるので、保存する時の表示でそう伝える

### 自動バックアップ

- `localStorage` に、版（リリース版 / 開発版）と機器の UID ごとに、直近 5 回分のスナップショットと日時を保存する。仕様の「直近の数回分」を 5 回とした。スナップショット1つは小さく、`localStorage` の容量に対して十分に収まる
- バックアップは、書き込みの一連の操作（再試行を含む）につき1回だけ取る。直前のバックアップと同じ内容なら増やさない
- 保存する形式に版の番号を入れる。スナップショットの形を変えた時に、古いバックアップを読めるようにするため
- 一覧から選ぶと、編集中の状態の「出発点」に入る。キーの動作への変換は通さないので、書き込むとバックアップと同じ内容になる
- バックアップは `.vil` として書き出せる。サイトのデータを消すとバックアップも消えるため
- 開発版とリリース版でバックアップが分かれていることを、一覧に表示する
- 保存に失敗した時（容量の上限、ブラウザーの設定）は、原因を示して書き込みを始めない。読み込みに失敗したバックアップ（形式が壊れている、版が読めない）は、一覧に「読み込めません」と出す

## 画面

```
┌ 非対応ブラウザーの警告（該当時は常時） ─────────────────┐
│ 接続状態 ・ 接続 / 切断 ・ 対応機能と残り枠数 ・ .vil 保存 / 読込 ・ 書き込み（変更 n 件） │
├ [キーマップ] [コンボ] ─────────────────────────────┤
│ レイヤー 0 1 2 3 …                                  │
│ キーボード図（エンコーダーを含む）                        │
│ 選んだキーの編集欄: タップ / 長押し / 2回タップ / タップ後長押し │
└──────────────────────────────────────────┘
```

- キーの上には動作を表示する（タップを大きく、長押しなどを小さく）
- 透過キーは、下のレイヤーで実際に効く動作を薄く表示する。「実際に効く」は、1つ下のレイヤーから順にレイヤー 0 までたどり、最初に見つかった透過でないキーの動作とする。どのレイヤーが有効かは使っている時の切り替えで変わるので、下のレイヤーがすべて有効な場合の表示である
- 対応機能（Tap Dance、Combo、エンコーダー、レイヤー切替の方式）と、Tap Dance・Combo の残り枠数を表示する。置き場所は画面デザインで決める
- 動作の選択は、分類のタブと名前での検索を持つ1つの部品にまとめ、4欄・エンコーダー・コンボの出力で共用する。欄ごとに選べない動作（「キーの動作のモデル」の決まり）は、選択肢に出さない
- 表示名は日本語にする（例: 「押している間だけレイヤー1」）。キーの刻印は US 配列で固定する

## テスト

- `model/` と `storage/`: 単体テスト。変換の往復、自動判定の表、枠の割り当て、差分、`.vil` の読み書き、「編集しなければ基準と一致する」こと
- `session/`: 偽の機器と偽の保存先を使った単体テスト。失敗する経路ごとに、本体が最後にどの状態になるか、バックアップに何が残るかを確かめる
  - 偽の機器には「N 番目の書き込みで失敗する」「途中で切断する」「読み直しで違う値を返す」を指定できるようにする
  - 確かめる経路: 途中の失敗からの再試行、途中の失敗からの復元、照合の不一致、書き込み前に本体が変わっていた場合、バックアップの保存の失敗、「書き込み中」の印が残った状態からの再開
- `device/vial/`: 要求を受けて応答を返す偽の transport を使った単体テスト。実機から取った応答を記録して使う。応答が待ち時間を超えて遅れる場合も含める
- 画面: 偽の機器を使って手で確認する。部品のテストは必要になったら `.test.tsx` に足す（テストの対象に `.test.tsx` を含める）
- 実機での確認: 完了条件に対応する手順を、作業ごとに PR に書く

## 後から変えにくい決定と理由

| 決定 | 理由 | 引き受けること |
| --- | --- | --- |
| スナップショットを本体の表現のまま持ち、`.vil`・バックアップ・差分の共通の形にする | 解釈できない内容を失わない。バックアップからの復元が、変換を通さずに済む | 変換のロジックと `.vil` が Vial 専用になる |
| 編集中の状態を、基準・出発点・編集の3つで持つ | 編集していない設定が書き込みで変わらないことを、状態の持ち方で保証する | 画面に出す値は、そのつど変換して作る |
| Tap Dance の番号を編集に持たず、目標を作る時に決める | 仕様の「番号は利用者に見せない」。番号の付け直しを1か所にまとめる | 既存の枠を動かさない決まり（「枠の割り当て」）が要る |
| 動作を `Action` と `KeyBehavior`（4欄）で表す | 仕様の4欄に対応する | 欄を増やす時は、ロジック・画面・テストのすべてに及ぶ |
| 機器のインターフェースは、まとめて読み、差分を書く | バックアップ・照合・差分の単位をそろえる。Bluetooth での通信を減らす | 1キーだけ読む、といった使い方はできない |
| バックアップを `localStorage` に、版と UID ごとに持つ | サーバーなしで、開発版がリリース版のバックアップを壊さない | サイトのデータを消すと消える（`.vil` への書き出しで補う） |
| 状態管理や UI のライブラリを入れない | 画面数が少なく、学習の負担を減らす | 後から入れることはできる |

## 実機で確かめること

結果はこの文書に反映する。

### 確認済み

- Bluetooth 接続の本体が WebHID の機器選択に出て、USB と同じ usage page の指定で接続できる（2026-10-10、接続と切断の画面で確認）

### 読み出しだけの最小版で確かめる

1. Bluetooth での応答の遅さと、全体の読み出しにかかる時間。応答が 1 秒を超えて遅れることがあるか、遅れた応答が後から届くか
2. VIA と Vial の各コマンドの応答が、要求と同じ内容（コマンド番号、位置）を先頭に含むか
3. 同じ機器を2つのタブで開けるか。開けた場合、応答は両方に届くか
4. 無操作で Bluetooth が切れるまでの時間
5. レイアウト定義を XZ 展開できるか、定義にエンコーダーが含まれるか
6. Vial の版と、キーコードの数値（基本キー、MO、TG、TO、OSL、LT、MT、Tap Dance）が QMK 版 Vial と同じか
7. Tap Dance と Combo の枠数、読み書きのコマンドが使えるか。Tap Dance の各枠が持つ時間の値をどう扱うか（新しい枠には既存の枠と同じ値を入れる想定）
8. RMK が対応しているレイヤー切替方式（OSL など）。参考: [Cornix の Vial キーの一覧](https://cornixhub.com/vial-keys) に MO・TG・TO・TT・DF・OSL・LT が載っている（対象のファームウェアの版や、動かないものの記載はない）。このサイトで使う MO・TG・TO・OSL・LT を、実機で1つずつ確かめる
9. 対象外の機能（マクロなど）がどのキーコードで現れるか
10. Vial が書き出した実物の `.vil` の形式（キーコードの持ち方、キーの並び順、マクロなどの項目）
11. 本体に Key Override の設定が入っているか（Vial の画面で見る）。マクロは使っていない（2026-10-10、利用者に確認）。入っていた場合は、`.vil` に含めない決定を見直す

### コンボを実装する前に確かめる

12. コンボがどのレイヤーのキーコードで判定されるか
13. 長押しなどを設定したキー（MT、LT、Tap Dance）をコンボに使うと、何のキーコードで判定されるか

### 書き込みを実装する時に確かめる

14. 書き込みにロック解除が要るか。要る場合は、その手順（本体のキーを押す、など）。要ると分かったら、「書き込みの流れ」の最初にロック解除の案内を足し、失敗の種類に「ロックされている」を足す
15. 書き込んだ設定が、電源を入れ直した後も残っているか
