# 設計

[docs/spec.md](spec.md) を実現するための設計。細部は実装しながら更新する。
「実機で確かめること」に挙げた項目は推測で書いており、最初の作業（読み出しだけの最小版）の結果で確定する。

## 方針

- 利用者が編集するのは「キーごとの動作」（タップ・長押し・2回タップ・タップ後長押し）だけにする。Vial のキーコードや Tap Dance の番号は、読み込み時と書き込み時にだけ変換して作る
- 通信（Vial）、変換と枠管理（純粋なロジック）、画面（React）を分ける。ロジックは実機なしで単体テストできる形にする
- 実機がなくても画面を開発・確認できるよう、本体の代わりになる偽の機器（メモリ上の実装）を用意する
- 依存ライブラリは最小限にする。状態管理や UI のライブラリは入れない

## 技術構成

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| 言語・UI・ビルド | TypeScript 7、React 19、Vite 8 | 仕様の指定 |
| パッケージ管理 | npm、Node.js 24（`.nvmrc`） | 追加の道具が要らない |
| テスト | Vitest | Vite の設定をそのまま使える |
| lint | oxlint | Vite の雛形の既定 |
| スタイル | 素の CSS（CSS Modules） | 画面数が少なく、UI ライブラリの学習が不要 |
| 状態管理 | React の `useReducer` と Context | 編集中の状態は1つのオブジェクトで足りる |
| CI | GitHub Actions（lint、型検査、テスト、ビルド） | PR ごとに実行 |
| 公開 | GitHub Pages（`main` への push で Actions からデプロイ） | 仕様の指定。public リポジトリの無料枠内 |

公開先は `https://usa0w0.github.io/cornix-keymapper/`。Vite の `base` を `/cornix-keymapper/` にしてある。

## 層と依存の向き

```
ui ──▶ model ──▶ device（インターフェースだけ）
 │                   ▲
 └──▶ storage        │ 実装
                 device/vial ──▶ WebHID
                 device/fake（開発・テスト用）
```

```
src/
  device/            機器との通信
    types.ts         機器に依存しないインターフェース（KeyboardDevice、KeyboardSnapshot）
    vial/            Vial の実装
      transport.ts   WebHID の送受信（32 バイトの要求と応答、直列化、タイムアウト）
      commands.ts    VIA / Vial のコマンド
      definition.ts  レイアウト定義（XZ 圧縮の JSON）の展開と解釈
      keycodes.ts    キーコード（数値）と動作（Action）の相互変換
      vialDevice.ts  KeyboardDevice の実装
    fake/            メモリ上の偽の機器
  model/             純粋なロジック（React にも WebHID にも依存しない）
    action.ts        動作の型と分類・日本語の表示名・検索
    behavior.ts      キーの動作（4欄）の型
    decode.ts        本体の設定 → キーの動作
    encode.ts        キーの動作 → 本体の設定（機能の自動判定、枠の割り当て）
    diff.ts          変更点の一覧
    transparent.ts   透過キーで実際に効く動作の解決
  storage/
    vil.ts           .vil の読み書き
    backup.ts        ブラウザ内の自動バックアップ
  ui/                React のコンポーネント
```

`model` と `ui` は `device/types.ts` だけを見て、`device/vial` を直接は参照しない。別のプロトコルの機器を足す時は `device/` の下に実装を増やす。

## 機器のインターフェース

本体の状態を、まとめて1つのスナップショットとして読み書きする。

```ts
interface KeyboardSnapshot {
  uid: string                      // 機器の識別（バックアップの鍵、.vil の照合）
  layout: LayoutDefinition         // キーの位置と大きさ、エンコーダーの位置
  capabilities: Capabilities       // レイヤー数、Tap Dance / Combo の枠数、使えるレイヤー切替方式
  keymap: number[][]               // [レイヤー][キー] = キーコード
  encoders: [number, number][][]   // [レイヤー][エンコーダー] = [左回し, 右回し]
  tapDances: TapDanceEntry[]       // 枠数ぶん
  combos: ComboEntry[]             // 枠数ぶん
  preserved: unknown               // このサイトで扱わない設定（マクロなど）。.vil に書き戻すために保持
}

interface KeyboardDevice {
  read(onProgress): Promise<KeyboardSnapshot>
  write(changes: Change[], onProgress): Promise<void>   // 差分だけを書く
  disconnect(): Promise<void>
}
```

スナップショットは「本体の表現」のまま持つ（キーコードは数値、Tap Dance は番号付き）。`.vil` とバックアップも同じスナップショットから作るので、このサイトが解釈できない内容も失わない。

## Vial の通信

- WebHID で、usage page `0xFF60`・usage `0x61` の HID インターフェースを `navigator.hid.requestDevice` のフィルターに指定する。USB と Bluetooth で同じ指定を使う
- 32 バイトの要求を送り、32 バイトの応答を1つ受け取る。要求は1つずつ直列に処理し、応答が来なければタイムアウトで失敗にして1回だけ再送する
- 使うコマンド

| 目的 | コマンド |
| --- | --- |
| 接続の確認、UID と Vial の版 | VIA `0x01`、Vial `0xFE 0x00` |
| レイアウト定義 | Vial `0xFE 0x01`（大きさ）、`0xFE 0x02`（32 バイトずつ） |
| レイヤー数、キーマップ | VIA `0x11`、`0x12`（まとめ読み）、`0x05`（1キー書き込み） |
| エンコーダー | Vial `0xFE 0x03`（読み）、`0xFE 0x04`（書き） |
| Tap Dance と Combo の枠数 | Vial `0xFE 0x0D 0x00` |
| Tap Dance | Vial `0xFE 0x0D 0x01`（読み）、`0x02`（書き） |
| Combo | Vial `0xFE 0x0D 0x03`（読み）、`0x04`（書き） |

- レイアウト定義は XZ 圧縮されている。ブラウザーに XZ の展開機能はないため、展開だけを行う小さなライブラリを1つ入れる（候補: `xz-decompress`。最初の作業で実機の定義を展開できるか確かめて決める）
- 定義の `layouts.keymap`（KLE 形式）から、キーの座標・行列上の位置・エンコーダーを取り出して描画する。配列はコードに持たない
- マクロ、Key Override、QMK Settings のコマンドは使わない。`.vil` に含まれていた場合は `preserved` として保持する

## キーの動作のモデル

```ts
type Action =
  | { kind: 'key'; code: number; mods: Mod[] }            // 文字・修飾キー・ショートカット・メディアなど
  | { kind: 'layer'; mode: 'momentary' | 'toggle' | 'to' | 'oneShot'; layer: number }
  | { kind: 'transparent' }
  | { kind: 'none' }
  | { kind: 'unsupported'; raw: number; label: string }   // マクロなど。編集不可、上書きは可

interface KeyBehavior {
  tap: Action
  hold?: Action
  doubleTap?: Action
  tapHold?: Action
}
```

画面の状態は、`KeyBehavior` をレイヤーとキーの数だけ並べたもの、エンコーダーの `Action`、コンボの一覧である。Tap Dance の番号は状態に持たない。

「ショートカット」は修飾キー付きのキー（例: Ctrl+C）として1つのキーコードで表す。

## 機能の自動判定

### 書き込む時（`KeyBehavior` → キーコード）

上から順に当てはめ、最初に合ったものを使う。

| 条件 | 使う機能 | 枠 |
| --- | --- | --- |
| タップだけ | そのキーコード1つ（タップ欄がレイヤー切替なら TG・TO・OSL・MO のキーコード） | 不要 |
| 長押しだけで、長押しが「押している間だけレイヤー N」 | MO(N) | 不要 |
| タップ＋長押しで、タップが修飾なしの基本キー、長押しが片側の修飾キーの組み合わせ | MT | 不要 |
| タップ＋長押しで、タップが修飾なしの基本キー、長押しが「押している間だけレイヤー N」（N は 0〜15） | LT | 不要 |
| 上記以外 | Tap Dance | 1つ |

MT と LT はキーコードの形に制約がある（タップ側は修飾なしの基本キーだけ、MT の修飾は左右どちらか片側だけ）。制約に合わない組み合わせは Tap Dance に回す。

### 読み込む時（キーコード → `KeyBehavior`）

逆向きに変換する。MO は長押し欄、MT と LT はタップ欄と長押し欄、Tap Dance は4欄に展開する。TG・TO・OSL はタップ欄のレイヤー切替になる。対象外の機能（マクロ、DF、TT など）と解釈できないキーコードは `unsupported` として元の値を保持する。

読み込んだ直後に何も編集せず書き込み用に変換した結果が、元のキーコードと一致することをテストで保証する（MT で書ける内容が Tap Dance で設定されていた場合などは、元の表現を保つ）。

### 枠の割り当て

枠の番号は状態に持たず、書き込み用に変換するたびに全体から計算する。

1. Tap Dance が必要な `KeyBehavior` を、全レイヤーのキーから集める
2. 内容が同じものを1つにまとめる（＝同じ内容のキーは1つの枠を共有する）
3. 読み込み時に同じ内容が入っていた枠があればその番号を使い、なければ空いている番号を使う（差分を小さくするため）
4. どのキーからも参照されなくなった枠は空きとして扱い、書き込み時に空の内容で上書きする

必要な枠の数が枠数を超える編集は、状態に反映する前に計算して止め、枠を使っているキーの一覧を出す。残り枠数は同じ計算から表示する。

共有は内容の一致で決まるので、「連動して変更」は同じ内容だった他のキーにも同じ編集を適用すること、「このキーだけ変更」は選んだキーだけを編集すること（内容が分かれるので枠が1つ増える）として実装する。

## コンボ

Vial のコンボは、キーの位置ではなくキーコードの組（最大4つ）と出力のキーコードで定義される。画面では「クリックしたキーの位置」で入力し、その位置のタップ欄のキーコードに直して保存する。読み込み時は、キーコードが一致する位置を探して図に示す。一致する位置がないコンボ（キーマップ変更で対応が外れたもの）は「対応するキーがない」と表示する。どのレイヤーのキーコードで判定されるかは実機で確かめる。

## 書き込みの流れ

1. 編集後の状態を本体の表現に変換し、読み込み時のスナップショットとの差分（`Change[]`）を作る
2. 差分を日本語の一覧で表示する（例: 「レイヤー1 の左手 3 行目 2 列目: 長押しを Ctrl から Shift に変更」）。個別に取り消せる
3. 「書き込み」で、まず本体から現在の設定を読み直してブラウザ内にバックアップする
4. Tap Dance → キーマップ → エンコーダー → コンボの順に書く（キーが参照する枠を先に用意する）
5. 全体を読み直し、意図した内容と照合する
6. 途中の失敗と照合の不一致は、失敗した項目と原因（切断、タイムアウト、不一致の箇所）を示し、「再試行」（残りの差分を計算し直して書く）と「書き込み前の状態に戻す」（バックアップとの差分を書く）を出す

どの操作も「目標のスナップショットと本体の現在値との差分を書く」という同じ処理で実現する。

## 保存

- `.vil`: Vial の JSON 形式。スナップショットと相互変換する。読み込んだ `.vil` は、いきなり書き込まず編集中の状態に入れ、通常の書き込みの流れ（差分の確認）を通す。UID が接続中の本体と違う時、レイヤー数やキー数が合わない時は読み込みを止めて理由を示す
- 自動バックアップ: `localStorage` に、機器の UID ごとに直近 5 回分のスナップショットと日時を保存する。一覧から選んで編集中の状態に戻せる

## 画面

```
┌ 非対応ブラウザーの警告（該当時は常時） ─────────────────┐
│ 接続状態 ・ 接続 / 切断 ・ 残り枠数 ・ .vil 保存 / 読込 ・ 書き込み（変更 n 件） │
├ [キーマップ] [コンボ] ─────────────────────────────┤
│ レイヤー 0 1 2 3 …                                  │
│ キーボード図（エンコーダーを含む）                        │
│ 選んだキーの編集欄: タップ / 長押し / 2回タップ / タップ後長押し │
└──────────────────────────────────────────┘
```

- キーの上には動作を表示する（タップを大きく、長押しなどを小さく）。透過キーは下のレイヤーで実際に効く動作を薄く表示する
- 動作の選択は、分類のタブと名前での検索を持つ1つの部品にまとめ、4欄・エンコーダー・コンボの出力で共用する
- 表示名は日本語にする（例: 「押している間だけレイヤー1」）。キーの刻印は US 配列で固定する

## テスト

- `model/` と `storage/`: 単体テスト。変換の往復、自動判定の表、枠の割り当て、差分、`.vil` の読み書き
- `device/vial/`: 要求を受けて応答を返す偽の transport を使った単体テスト。実機から取った応答を記録して使う
- 画面: 偽の機器を使って手で確認する。部品のテストは必要になったら足す
- 実機での確認: 完了条件に対応する手順を、作業ごとに PR に書く

## 実機で確かめること

最初の作業で、読み出しだけの最小版を使って確かめる。結果はこの文書に反映する。

1. Bluetooth 接続の本体が WebHID の機器選択に出るか、USB と同じ usage page で通信できるか（OS は macOS を想定）
2. Bluetooth での応答の遅さと、全体の読み出しにかかる時間
3. レイアウト定義を XZ 展開できるか、定義にエンコーダーが含まれるか
4. Vial の版と、キーコードの数値（MO、TG、TO、OSL、LT、MT、Tap Dance）が QMK 版 Vial と同じか
5. Tap Dance と Combo の枠数、読み書きのコマンドが使えるか。Tap Dance の各枠が持つ時間の値をどう扱うか（新しい枠には既存の枠と同じ値を入れる想定）
6. RMK が対応しているレイヤー切替方式（OSL など）
7. コンボがどのレイヤーのキーコードで判定されるか
8. 書き込みにロック解除が要るか
9. 対象外の機能（マクロなど）がどのキーコードで現れるか

## 作業の分割（案）

設計のマージ後、次の単位でこのリポジトリの issue を切る。上から順に進める。

1. GitHub Pages へのデプロイ
2. WebHID の transport と接続 UI（USB / Bluetooth）、非対応ブラウザーの警告
3. 読み出しだけの最小版（定義・枠数・キーマップなどを読んで生の値を表示）と実機確認、設計の更新
4. 偽の機器
5. キーコードと `Action` の相互変換、日本語の表示名
6. レイアウト定義からのキーボード図の描画、レイヤー切り替え表示、透過キーの表示
7. `KeyBehavior` の読み込み変換（decode）と、キー上の表示
8. 動作を選ぶ部品（分類と検索）
9. キーの編集欄と自動判定（encode）、枠の割り当て、残り枠数と枠不足の表示
10. 共有中のキーの変更確認（連動 / このキーだけ）
11. エンコーダーの編集
12. コンボのタブ
13. 差分の一覧と取り消し
14. 書き込み、照合、自動バックアップ、失敗時の再試行と復元
15. `.vil` の保存と読込
16. リリース前の確認（完了条件を実機で1つずつ確かめる）
